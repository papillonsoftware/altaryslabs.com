### Blockers

- [ ] **[BLOCKER]** `src/components/ContactContent.astro:180` - the Turnstile widget carries no `data-language`, so it renders in the **browser's** language and not the page's. Verified on the rendered page, not inferred: `/en/contact` serves `<html lang="en">` and the widget inside it displays **"Vérification..."**, in French (capture `en-contact-768.png`, and identically at 1440 px). `grep -c data-language dist/en/contact/index.html` returns `0` on both built contact pages, and Turnstile's documented default for that attribute is `auto`, which follows `Accept-Language`. Two consequences, both real: a French string ships inside an English page, which the bilingual-parity rule treats as a critical failure, and the French fragment carries no `lang="fr"`, which is a WCAG 3.1.2 Language of Parts failure. The exposure is not marginal here, it is the common case: the target market's browsers are overwhelmingly French-configured, so the English contact page shows a French anti-robot control to most of the anglophone-facing audience it exists for, on the one page where a prospect is about to hand over their name. -> Pass the page language explicitly: `data-language={locale}` on that div. The value is already in scope in the component.

### Important

- [ ] **[IMPORTANT]** `functions/api/contact.ts:190-197,209-216` with `src/components/ContactContent.astro:83` - **every failure path silently discards everything the visitor typed.** The handler answers `303` to a fully static page, so the form the visitor lands on is blank, while the panel above it says "Votre message n'a pas pu etre transmis. Verifiez votre connexion et reessayez dans quelques instants." Verified visually at `/en/contact?statut=erreur`, 360 px: the error panel sits above a completely empty form. The instruction to retry is one the page has made impossible to follow without retyping the whole message. D092 justifies POST-then-redirect by the double-send it prevents on **success**, and that reasoning is sound; it never addresses the mirror cost on the **error** side, and D097 asserts "the error state is the only honest answer" without noticing that the honest answer arrives with the message deleted. For a director writing several paragraphs about a 20 to 100 million FCFA tender, one refused token costs the whole enquiry, and the likeliest outcome is that they do not retype it. -> Preserve the input across the redirect. The smallest change consistent with D092 is to persist the field values to `sessionStorage` on submit and rehydrate them when `?statut=erreur` is read by the inline script at line 190; a server-side alternative is to echo the submitted values back in the redirect, which is heavier and leaks content into the URL. Either way the decision belongs in a D-row, because it amends D092.

- [ ] **[IMPORTANT]** `src/components/ContactContent.astro:75,190-209` - **the error panel is never announced and never receives focus, and `role="alert"` on it is a no-op.** The inline script only sets `panneau.hidden = false`, during document parsing. A live region revealed before the first render is part of the initial page state, not a change to it, so assistive technology has nothing to announce; and neither `#form-sent` nor `#form-error` carries `tabindex="-1"`, so even adding a `.focus()` call would do nothing today. This is a regression against what the branch previously shipped: the D064 stopgap this PR deletes did carry `tabindex="-1"` on `#form-pending` and did call `pending.focus()`. It is also a carry-over the previous round explicitly assigned here, `docs/reviews/PAGE-002-review.md` round 1 on `ContactContent.astro:221-226`: "moving focus to the panel would also serve a magnifier user. -> Optional, and it belongs with FORM-001 if the real error path gets the same treatment." The real error path arrived without the treatment, and `docs/work-items/FORM-001.md` does not mention focus at all. -> Add `tabindex="-1"` to both panels and move focus to the revealed one, reusing the reduced-motion-aware scroll the deleted script already got right.

- [ ] **[IMPORTANT]** `server/turnstile.ts:78-81` - the `hostname` field of the `siteverify` response is read and discarded, so **a token minted on any hostname the widget allows is accepted from any other**. The widget's allowlist is `altaryslabs.com`, `altaryslabscom.pages.dev` and `localhost`. `localhost` is the problem: the site key is public by design and sits in the served HTML, so anyone can serve a page locally with that key, solve the challenge, and post the resulting token to production, which will validate it. That is the whole of acceptance criterion 2, and it is bypassable by design rather than by accident. `docs/work-items/FORM-001.md:142-150` already names this as "a candidate for the review rounds, deliberately not done here", which is the right call on scope but does not make the exposure smaller. -> Return `hostname` in `TurnstileVerdict` and reject any value outside an explicit allowlist, or drop `localhost` from the widget once local testing is done. Under the maximal bar an acknowledged defect is still a defect; it blocks and it is tracked.
